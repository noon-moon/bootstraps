# Optional experiment batches

Read only when the user requests task-backed experiment batches or parallel inquiry paths. The default remains one task and one bounded sequential loop with an approved positive integer iteration count before dispatch. Do not reconfirm a supplied or agreed count. A generation is an iteration: implementation -> evidence -> independent experimental review. Unsuccessful iterations count; substantive retuning consumes a new slot. Stop at the approved count or early success/blocker and ask for approval before extending it.

## Task-based experiments and parallel work

Use one durable task per falsifiable experiment, not one per agent. Prefer the project's existing task tracker; Backlog.md is an optional adapter, not a required CLI for every domain. Record the user-requested batch count, category quotas and whether ongoing work counts toward them. Reserve requested slots/category quotas without pre-deciding every hypothesis. Fill later briefs from preceding evidence and primarily parallelize distinct inquiry paths. A reserved slot is not ready: show "Reserved: awaiting prior review" until the reviewer supplies its hypothesis and criteria. New queued ideas do not authorize implementation or increase those limits. Allocate slots across all parallel pairs from the same approved budget, not a separate implicit budget per worker.

The reviewer owns the hypothesis, proposed mechanism and decision criteria. A ready task records: observed gap and expected difference; source proposal and execution authorization; owned files and exclusions; frozen baseline commit, scene/seed/settings and control evidence; smallest useful comparison and required regression views; and genuine prerequisite outputs. Capture incomplete ideas as drafts. Reserve IDs through one owner before parallel task creation when checkout-local allocation can collide. Adapt existing status/dependency/reference fields rather than adding a scheduler or database.

The orchestrator dispatches ready independent investigation and implementation concurrently in separate worktrees, with declared file ownership. Overlapping edits are either serialized or explicit competing alternatives from one baseline; never assume those branches are mergeable. On a shared single host, serialize heavy builds, GPU captures and performance measurements, tracking resource ownership in the ledger. Light work and independent reviews can continue while unrelated implementation proceeds; a verifier need not wait for the whole batch.

Use isolated branch-sensitive build outputs, or explicitly invalidate local-package artifacts for the relevant profiles before switching source variants in a shared target. Verify fresh local compilation and preserve build logs, dependency metadata and exact executable hashes; archive executables when practical. A source-revision sidecar alone does not establish what produced the evidence.

The implementer freezes its source revision and hands off reproduction commands, immutable evidence/manifest, measurements and limitations. A separate reviewer inspects control/result evidence before implementation self-assessment, then checks source and measurement claims. Record hypothesis outcome (supported/rejected/inconclusive), evidence, limitations and a separate adoption decision. A verified negative or inconclusive experiment can be complete without completing its parent product request and still consumes an iteration. A changed mechanism becomes a linked follow-up task and consumes a new iteration; retain immutable attempt IDs for repairs/reruns within the existing authorization. Capture-only retries stay within the same image budget (16 review images per iteration unless overridden), without a new iteration. Build-only repairs may restore the intended implementation within its slot but must record reason, changes, revision and validation; substantive retuning is never a free repair.

Adoption and integration are distinct: successful isolated candidates require a fresh combined render/evidence set and independent review before claiming the integrated state works. Plan that integration within the authorized batch or leave it explicitly pending; do not add an automatic extra cycle. Record the integration revision separately. Use `run-as-orchestrator`, `run-as-implementer` and `run-as-experimental-reviewer` for their roles. Any PR additionally requires a separate `run-as-code-reviewer`; experimental evidence review is not the code gate. Keep task lifecycle in the tracker, ownership/resources in the ledger and evidence/review history in the existing records or explicitly requested shared gallery. Label each current/new gallery entry with its task-derived E identity, retaining legacy physical folders. For independent experiments, set explicit incoming guidance from their actual proposal/dependencies; the builder's preceding-folder fallback is only appropriate for sequential chains.

When the user explicitly requests a final integration experiment after the exploratory batch, allocate it a separate task and count, preserving the exploratory quota. Include only accepted candidates and integrate through the repository's normal review/landing process within existing authorization and policy. Record candidate acceptance, integration commits and selected configuration. If the requested evidence must represent main, capture from a clean build worktree exactly at the recorded main revision; an unmerged candidate branch is not main. Complete the final independent review before any dependent analysis. This authorized stage does not permit extra corrective iterations; leave remaining failures explicit unless further work is authorized.
